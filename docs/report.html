The problem

“The connection stayed alive” is not the success criterion

An inspection robot moving through a site is surrounded by several networks at once: indoor Wi‑Fi, private 5G, satellite, a wired dock. Today it uses one, waits for it to break, and only then looks for another. By then the frame is late and the operator is looking at the past.

Fixing the transport is not enough, and this is the part that is easy to miss. QUIC can already carry a connection across a network change without dropping it. But if the compute you are talking to is still the box you started with, you are now reaching a distant server over a worse path. Nothing looks broken. Everything is slower.

What the operator actually feels is not one number but four, and every one of them moves when the robot moves:

end‑to‑end = network round trip + queueing + inference time + response transit

So ECHO watches all four networks and all four edge sites continuously, predicts which pair is about to be best, and migrates the live inference session there before the current path degrades — with the old edge still serving until the new one has proved it works.

How it fits together

One robot, four networks, four places to compute

The agents

Nine agents, each answering a different question

Splitting these apart is not decoration. “Which pair is best?” and “should we move right now?” are genuinely different questions, and conflating them is how a system ends up thrashing on a correct ranking at the wrong moment.

01

Watcher

What does every network and every edge look like right now — including the ones nobody is using? You cannot switch to a link you were not already watching.

02

Predictor

Where is each one heading? EWMA level plus a least-squares slope over a 10 s window, extrapolated 2 s ahead.

03

Intent

What is the robot doing? A call wants steadiness, a download wants throughput, live inference wants the lowest total time. Each gets a different weight vector.

04

Decision

Which (network, edge) pair has the lowest predicted end‑to‑end cost? Scores all 16 pairs, with hysteresis so it does not oscillate.

05

Orchestrator

Act on that now, or hold? Enforces one move at a time, a 3 s cooldown, and Recovery's backoff — then picks the cheapest action that achieves the goal.

06

Handoff

Runs the six‑message sequence, early and reversibly. Nothing is discarded until the target acknowledges.

07

Recovery

The handoff failed — stay, retry elsewhere, or cold‑start? Backs off the edge that failed so it does not get an immediate second try.

08

Troubleshooter

It feels bad and nothing switched. Why? Separates congestion, coverage, instability, loss, edge load and simply being compute‑bound.

09

Explainer

Says it in one sentence, generated from the same numbers the decision used, so the explanation cannot drift from the reason.

—

Cost

Planned. Avoid a metered link when a free one is comparable.

—

Security

Planned. Avoid untrusted networks such as open public Wi‑Fi.

—

Energy

Planned. Balance battery against continuously probing four links.

—

Policy

Planned. Fixed rules, e.g. calls always get the most reliable option.

—

Learning

Planned. Remember that a link reliably degrades at a given time and prepare ahead of it.

The scoring function is over the pair, never the network alone, and over predicted state rather than current:

score = w₁·predicted_path_rtt + w₂·predicted_jitter + w₃·predicted_loss
       + w₄·predicted_inference_ms + w₅·edge_load + w₆·proximity_cost

The weights come from the Intent Agent. A challenger must beat the incumbent by 12% for 3 consecutive ticks before a handoff is authorised — unless the current path is already unreachable, in which case hysteresis is skipped.

The protocol

What actually crosses during a handoff

The model is already resident on every edge. Only the live session travels, which is why a handoff costs milliseconds instead of a model download.

  1. 01PREPARETarget allocates resources for the session. No model transfer — it is already there.
  2. 02STATESession id, model id and version, last processed frame, state version, and the object‑tracking state cross the wire. Roughly 300 bytes.
  3. 03READYTarget confirms it reconstructed the session. Because state arrived, it carries no cold‑start penalty.
  4. 04VERIFYTarget infers one duplicate frame. A broken target is caught before commit, while the old edge is still serving.
  5. 05COMMITTarget becomes the active inference server. Only now does the client stop sending to the old edge.
  6. 06DRAINOld edge finishes outstanding work and accepts no more. Its connection is closed on a delay so in‑flight frames still land.

Two properties make this safe rather than merely fast. It starts early, triggered by the Predictor's trend rather than by a failure. And nothing is discarded until the target acknowledges, so a failed handoff costs one wasted attempt and the session never leaves the old edge.

Method

What is held identical across the three experiments

The only thing that varies between the three runs is the client's decision logic — one branch in client.py. Everything else is the same code path.

Held constant

Same route and timing, same four network profiles, same random seed, same 90 s duration, same 20 fps workload, same four edge servers, same simulated inference cost, same measurement code.

The zone‑crossing windows used for scoring are fixed positions on the route, identical for every mode, so a mode cannot improve its score by declaring fewer transitions.

What varies

TCP. No migration, no prediction. React after the break, reconnect, rebuild the session from nothing.

QUIC only. The connection survives a network change, but the compute never moves. The interesting baseline, because nothing looks broken.

QUIC + ECHO. The full agent stack.

Reading this honestly

This is one run at one seed. Most columns are stable across seeds. One is not: QUIC‑only's inference latency gap has measured anywhere from 3 ms to 40 ms across runs, because it depends on exactly when its migration lands relative to a crossing window. A judge who re-runs this with a different seed will see a different number there, and that is expected.

When that figure comes out low, it is not QUIC‑only doing well. It is QUIC‑only being uniformly worse: holding a connection to an edge it should have left, so its settled latency is already high and a zone crossing barely moves it. Measured against itself it looks stable. Measured against what the robot should have been getting, it spends 71 of 90 seconds on the wrong edge.

So the gap metric is not the argument on its own — it is only meaningful beside the absolute numbers. ECHO has the lowest p95, the lowest median, the lowest p99, the shortest freeze, no losses and no reconnects, and 6.8 s on a suboptimal edge instead of 71 — while performing four live session migrations.

Credibility

What is real, what is emulated, what is simulated

Stated plainly, because it is the first thing a judge should ask, and because a prototype that overstates itself is worth less than one that does not.

Real

The QUIC stack (aioquic), the TLS handshake, and connection migration across a genuinely different four‑tuple — same connection ID, server‑side path validation, no new handshake.

All four edge sites as independent services speaking the full ECHO message set over both QUIC and TCP. Real UDP and TCP sockets. Every latency figure measured end‑to‑end from the client, not modelled.

Emulated

The link conditions. Delay, jitter, loss and bandwidth are applied by relays sitting between client and edge, driven by a coverage model — which is what tc/netem does, moved into userspace so the whole thing runs on one laptop of any OS.

The relay identifies which network a packet belongs to by the client's source port, which is also what makes migration observable. On Linux the same numbers can drive real tc qdiscs across namespaces; nothing else changes.

Simulated

The inference itself — a controlled delay that responds to edge load and to whether the session was warm‑started from transferred state or rebuilt cold.

What this project measures is end‑to‑end inference latency and session continuity across a handoff, not the accuracy of a detector. Swapping in a real YOLO forward pass means replacing one method, EdgeService._infer, and nothing else.

Limitations

What I would fix next, and why

Two of the four handoffs were probably unnecessary

The session moved A→B at 2.1 s, back B→A at 5.9 s, then A→B again at 21.0 s — all while the robot was still in Zone A. After that it was stable: Edge B until 73.1 s, then Edge D at the dock.

The cause is that the Predictor's window is still filling in the first few seconds, so its trend estimate is noisy, and Edge A and Edge B genuinely score close together in Zone A. Hysteresis and the Orchestrator's cooldown limited the thrash but did not eliminate it. The fix is a warmup gate — the Orchestrator should refuse to authorise a move until the Watcher holds a minimum number of samples. That is a small change and it is the first thing I would do.

  • Edge health is read in‑process, not probed over the wire. The Watcher calls each edge's health() directly rather than sending an ECHO_METRICS probe through the relay. That is a control‑plane shortcut; it keeps the focus on the handoff, but it means edge health carries no measured probe latency.
  • All four edges are asyncio tasks in one process. They are independent services with independent state, but they share a CPU, so the simulated inference cost is more trustworthy than a real one would be under contention.
  • TCP loss is modelled as retransmission delay, not dropped bytes. Dropping bytes from a stream would corrupt it; real TCP turns loss into delay anyway. The baseline is still a competently written pipelined client, not a straw man.
  • Single‑seed results. A proper evaluation would run each mode across many seeds and report distributions rather than one number per cell.
  • The preload buffer is decided but not yet exercised. The Intent Agent correctly identifies live traffic as unbufferable and reports how much it would pre‑fetch for non‑live traffic, but the robot workload is live, so the buffer never engages in these runs.
  • Five agents are designed but not built — Cost, Security, Energy, Policy and Learning. The weight vector in config.py is the seam they plug into.

Running it

Everything is in the project folder

Nothing is installed outside it. Deleting the folder removes every trace.

# set up
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

# run all three experiments and rebuild the figures
.venv/bin/python scripts/run_experiments.py --duration 90 --seed 7
.venv/bin/python scripts/plot_results.py

# watch it live in 3D at http://127.0.0.1:8080
.venv/bin/python dashboard/server.py

# tests
.venv/bin/python -m pytest -q

The dashboard is a third‑person 3D view of the robot walking the route, with all four networks and all six characteristics each, all four edge sites, the nine‑agent pipeline showing what every agent currently believes, and a plain‑language line explaining each decision as it is made. The browser is fed the same event stream the log file records, so what is on screen and what the numbers say cannot disagree.
